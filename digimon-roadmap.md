# Digimon asset-library roadmap

v1.0 scope includes only sections 1, 2 and 3, in order to flesh out the original game with a more complete cast of popular digimon from shows and games during the game's global release year. Sections 4 and 5 are less defined expansions intended for post-game content in later revisions of this project.

## Status key

Track each area independently: **Art** covers models, textures and animations; **Techniques** covers assigned attacks, finishers, effects and learning; **Evo requirements** covers parents, raising conditions and evolution routes.

| Status | Meaning |
|---|---|
| not started | No implementation is recorded for this area. |
| in-progress | Work exists or has begun, but playability in this area has not yet been confirmed. |
| playable | Usable in the game; polish, balancing or broader validation remains. |
| completed | Finished, reviewed and validated for the intended role, with no planned work remaining in this area. |

Playable updates reflect the project status reported on 2026-11-05. Being raisable confirms playable art and evolution requirements; technique status remains in-progress until separately confirmed. Existing inventory entries retain in-progress status where no newer confirmation is available.

## Purpose and release boundary

Prioritize complete, recognizable families, then supporting species and regional variety. Follow the numbered order within each section; fixes to released content take precedence.

Use assets from **Digimon World 1, Digimon World 2, Digimon World 2003 and Digital Card Battle**. The project can also use hand-authored assets, as with the babies. Other candidates need a model from those discs or an agreed hand-authoring plan before implementation.

All species in this section are already in the game and raisable. Polish the core families first, then the hand-authored nursery forms and supporting roster. The babies are playable and can be refined over time without adding donor discs.

The lower-priority species in section 3 still fit the vanilla aesthetic; they add regional variety rather than closing the core family gaps. Mammothmon and SkullMeramon are included in the first section to flesh out the limited number of ultimates in the vanilla game, but can be deferred to section 3 if needed.

## Acceptance: when a row advances

Use the intended role to scope acceptance: partner, enemy, NPC or several. **Partner is the default**; a row explicitly scoped first to a boss/NPC can be accepted for that role, but must say so and cannot be advertised as a complete raisable partner. If roles finish separately, split the row or link a role checklist; record completion separately in each status column.

1. **Reconstructible asset.** Record the source/authoring recipe, tool revision and content identity. The supported local build reproduces the asset; publish the permitted authored inputs/recipes and evidence metadata, not donor disc data. Reuse existing native assets and IDs when appropriate.
2. **Art.** Review silhouette, texture/palette, rig deformation, scale and contacts in the game. For partners, cover idle, walk/run/turn, follow, eating, sleeping, toilet, happiness/refusal/sickness, training, evolution and battle states that the runtime calls. For babies and NPCs, document legitimate non-applicable states or techniques; mark that area completed only once its intended coverage is confirmed. Export success and one idle screenshot are insufficient.
3. **Techniques and evo requirements.** Validate technique learning/equipping and every assigned attack and finisher: animation, contact/projectile origin, effects, hit/damage timing and recovery. Separately validate parents, raising conditions, competing branches, natural/item evolution and rebirth through actual raising routes. Check care/food/sleep/training, battle completion and save/reload as applicable. Check enemy/NPC-only roles through their real placement, interaction and persistence paths. Compare balance with named vanilla peers and a defined profile; define a useful regional role rather than making every addition stronger.
4. **Options and capacity.** Exercise NEW DIGIMON on/off with a valid fallback and restoration; EXTENDED STORY on/off with library use independent of demo flags; NORMAL/EASY for battle roles; 20/60 FPS for motion/effects. Check the supported 2 MB configuration, model/animation/heap limits, dense scenes and overlay transitions. Record emulator/CPU/RAM settings and distinguish optional overclock/8 MB results from the standard configuration.
5. **Evidence and regression.** Link the exact tested commit, build configuration, commands, results and visual-review evidence from the row. Check unaffected peers when shared retargeting/effect code changes. Reopen acceptance when its model, animation, attack, evolution or shared runtime dependencies change materially.

## Decisions to make before expanding the commitment

- **V1.0 roster:** complete sections 1–3 in priority order and resolve optional forms. Sections 4–5 outline later post-game expansions.
- **Profiles:** define the supported roster, balance and story combinations. NEW DIGIMON OFF currently limits species; it does not undo the unconditional care/economy rebalancing described in [balance.md](docs/mods/balance.md). EASY/NORMAL is a combat multiplier, not a complete classic/expanded ruleset switch.
- **Save semantics:** keep species IDs and mod-owned flags stable. Document fallbacks, restored partners, retained recruitment and story-removal behavior using the existing [options](docs/mods/options.md) and [compatibility](docs/mods/compatibility.md) contracts. Test two saves with different options, not only one save round trips.
- **Library boundary:** demonstrate one standalone mini-mod using a polished family, one encounter/resident and a save round trip with the beta story disabled. This is a practical acceptance test for the framework claim. A new story, a fusion system and every late boss can remain separate consumers of that library.
